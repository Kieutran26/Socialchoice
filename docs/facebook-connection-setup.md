# Facebook Pages connection

Implemented connection code: server OAuth code exchange, long-lived user-token exchange, Page discovery, selected Page import, encrypted Page tokens, reconnect, Page-access check and local disconnect. The app requests `pages_show_list`, `pages_read_engagement`, `pages_manage_posts` and `pages_read_user_content`. Existing read-only connections must reconnect and import the selected Page again to obtain publishing permission and fresh Page task metadata. No real connection is claimed until the owner completes a real Meta flow. No test Pages or fake tokens are inserted by runtime.

## Owner setup

Recommended on Windows: run `npm run setup:meta`. Enter App ID, the supported Graph API version, callback URI and optional Login configuration ID; enter App Secret in the hidden prompt. This creates ignored `.env.meta` and generates the encryption key automatically. It refuses to overwrite an existing configuration/key and prints no secret. `npm start` and `npm run dev:api` load this file after `.env.local`. Preserve/restrict/back up it privately; edit it locally for later App changes while keeping the encryption key. No credential has been supplied through chat or generated for a real Meta account by the assistant. The manual alternative below is for owners managing environment files themselves.

1. In [Meta for Developers](https://developers.facebook.com/apps/), create/configure your app with a Facebook Login flow eligible for Pages access. Use an account authorized to administer the test Page. Configure permissions/access in the app dashboard. App roles, App Review, Advanced Access and business verification may affect who can authorize the app. Creating an app does not automatically grant those approvals.
2. Register the exact callback as a Valid OAuth Redirect URI. For the one-process local app: `http://127.0.0.1:3001/api/meta/callback`. If Meta refuses HTTP/loopback for your app's mode, use a properly configured HTTPS deployment and register its exact callback. Do not expose unauthenticated local development through a tunnel. For Vite development use the frontend origin/port in the callback, since browser cookies belong to that origin.
3. Set server-only values in `.env.local`: `META_APP_ID`, `META_APP_SECRET`, `META_GRAPH_VERSION` (supported version from your app dashboard), `META_REDIRECT_URI`, `META_TOKEN_ENCRYPTION_KEY`. If your Facebook Login for Business setup requires a configuration ID, also set `META_LOGIN_CONFIG_ID`. Do not put any secrets in `VITE_*`, frontend fields, Git or chat. `ready` only means local configuration is valid, not Meta approval or API access.
4. Generate the encryption key once on your machine. This command places it in a separate ignored file for local transfer into `.env.local`, without printing it: `node --input-type=module -e "import {randomBytes} from 'node:crypto'; import {writeFileSync} from 'node:fs'; writeFileSync('.env.meta-key', 'META_TOKEN_ENCRYPTION_KEY='+randomBytes(32).toString('hex')+'\n', {flag:'wx',mode:0o600})"`. Copy that line locally into `.env.local`. Keep a private backup of the key, restrict Windows file permissions and do not regenerate it while stored connections exist. Loss/change of the key requires reconnection. Never send the key here.
5. Ensure the Socialchoice admin password has been set with `npm run setup:admin`. Rebuild (`npm run build`) and restart your existing app (`npm start`), or restart the development API/frontend pair. Stop/restart your current server rather than starting duplicates.
6. Sign in, create a real active brand, then open Social Accounts → choose brand → Connect / reconnect Facebook. Sign in only on Facebook's official domain. Grant the allowed Page permissions. On return, choose the Pages actually returned by Meta and click Connect selected Pages. Select within ten minutes; restart/expiry requires starting OAuth again.

Keep browser hosts consistent: do not alternate `localhost` and `127.0.0.1`. The callback origin must match the app origin you use in the browser. For public HTTPS, it must match `SOCIALCHOICE_PUBLIC_ORIGIN`. The proxy's backend Host must match `SOCIALCHOICE_BACKEND_ORIGIN` for the Node backend. The Cloudflare backend and Vercel same-origin API are now deployed and verified; see online-deployment.md.

## Behavior and safety

- No Facebook password is collected by Socialchoice. OAuth code exchange happens on the server. A random single-use ten-minute state and separate HttpOnly SameSite=Lax flow cookie are bound to an active admin session. This permits the external callback while keeping the admin cookie SameSite=Strict.
- Page tokens remain in a private SQLite table as AES-256-GCM ciphertext with record-bound authentication. Generic entity APIs cannot read that table or assign connected/credential metadata. Page names, IDs, granted scope names and an opaque credential ID are safe metadata; no token goes to the browser.
- Unselected Page tokens stay in temporary server memory locally; the cloud adapter encrypts pending selections in private SQLite storage so they survive actor restarts until expiry/import. The user token is used to discover Pages and is not persisted. Each imported Page stores its own token. Reconnect repeats Meta authorization and updates the selected Page's credential for the same brand/ID; multiple authorized Facebook profiles can be connected in successive flows. Facebook may reuse its active browser profile; switch profiles on Facebook itself, not by entering another profile's password in this app.
- Check Facebook access makes a real Page identity request. `connected` records a successful authorization/import or last successful access check, not a promise that the token is still valid or can publish. Known authorization failure marks it expired; transport failures do not fabricate expiry. Reconnect handles token expiry/revocation. There is no background refresh or platform deauthorization webhook yet.
- Disconnect deletes the local credential and keeps the destination/history. It does not revoke all permissions for the Facebook profile, which could affect other connected Pages. To remove the app's authorization at Meta, use Facebook's app/business integration settings; then check/reconnect affected Pages locally. Deletion requires disconnect first and continues to preserve publishing history.
- Publish Now requires a live draft, 1–30 different connected Facebook Pages within the same live brand, supported private media or text, pages_manage_posts in both verified account and encrypted credential metadata, and CREATE_CONTENT or PROFILE_PLUS_CREATE_CONTENT in the Page tasks. Automatic delivery requires explicit reviewed scheduling; reaction/comment/share retrieval is implemented; see [analytics](facebook-analytics.md). Reach/view metrics remain unavailable.

## Empty Page enumeration fallback — 26 October 2026

In the pending Facebook Page selection, **Reload Page list** starts a fresh official Facebook authorization and discovery using the selected brand. It does not reread the cached selection. To include Pages outside the current grant, use Facebook's **Edit settings** and explicitly allow those Pages before continuing. Reload itself neither disconnects existing channels nor imports new ones; review the returned list and connect selected Pages. A cancelled flow keeps connected channels intact; start/reload again to obtain a fresh pending selection. No long-lived USER token is stored for this feature.

If Facebook completes `me/accounts` with an empty list, the backend checks the existing USER token through Meta `debug_token`. Only numeric Page IDs from the provider's `pages_show_list` granular grant are candidates (maximum 100). Each direct Page token must independently match the same App, user and Page and pass validity/expiry checks. This does not add scopes or require a manually entered Page ID.

Direct Page objects do not expose `tasks`; the backend never invents them. Publishing preflight accepts either existing content-creation tasks or an encrypted, exact-token-bound proof with target-specific `pages_manage_posts` and `pages_read_engagement` grants on both USER and PAGE tokens. Existing scope checks and confirmation requirements remain. Public selection responses omit tokens and private grant proof. Normal nonempty enumeration and Instagram discovery are unchanged.

## Text Publish Now

Add pages_manage_posts to the app’s Pages use case with owner consent, complete Meta’s required access/testing steps, then reconnect under Social Accounts and import the intended Page. App dashboard permission availability does not by itself grant a token permission or prove publication.

In Create Post, choose 1–30 authorized Pages from the same brand, enter the shared text and optional per-Page captions (per-Page overrides take precedence over the Facebook caption and common caption), then Publish now. The backend stores a ten-minute review of every exact Page and caption. Confirm and publish sends one independently claimed POST per Page to the official Graph Page /feed endpoint using the encrypted server-side Page token. Changed drafts, changed credentials or expired reviews require a fresh review.

A synchronous SQLite transaction claims the private attempt before network I/O and records an immutable variant/job. Repeated confirmations return the existing result. Only a valid Page-prefixed Meta post ID enables Published, published_at and a Facebook link. Generic CRUD cannot forge confirmations or alter/delete attempted history. The Facebook URL is formed from the confirmed ID; an independently fetched permalink is not claimed.

Timeouts, transport errors, malformed responses and ambiguous errors become Delivery unconfirmed, never an automatic resend. Interrupted processing becomes unconfirmed after sixty seconds when its status is checked; opening processing history checks that status. Check the Page before duplicating an uncertain post. Definite publishing-permission/token denials become Failed and retain history. Old calendar plans do not automatically publish. New automatic schedules require explicit confirmation; see [scheduling](facebook-scheduling.md). Multi-Page delivery uses separate private attempts/jobs and group approval; see [multi-Page operations](facebook-multi-page.md).

Validation uses isolated SQLite and the actual Workers runtime; no mocked successful Meta post is used. On 2026-10-12, the owner approved adding pages_manage_posts, reauthorized only the current Deszy Page, imported the renewed credential and approved the exact technical test text. Publish Now returned a valid Facebook post ID and the post was independently opened on Facebook, confirming the Page, text and Public visibility. See plans/reports/facebook-text-publishing-261012-report.md for the recorded result. The Meta app remains unpublished; this successful authorized Page test does not claim Advanced Access or general public approval.

## Photo Publish Now

The same pages_manage_posts and content creation Page task are used. Upload private images under the live brand, select 1–30 Pages within the same brand, enter the caption and confirm the exact ordered images. The backend sends multipart source files to Page /photos with published=false, validates each photo ID, then sends attached_media to Page /feed. Tokens never enter the browser or a media URL. Only a confirmed final Page-prefixed post ID marks Published.

The server stores each operation claim before the remote call. A repeated or interrupted alarm cannot upload/publish the same uncertain operation again. Completed image uploads have durable checkpoints. Unknown outcomes keep history; inspect the Page before duplicating. Uploaded unpublished photo IDs are retained for diagnosis but automatic cleanup/deletion at Meta is not performed.

Private files use the existing SQLite backend rather than a new paid storage product: 3 MiB per file, JPEG/PNG/still WebP, up to ten per post, 200 MiB encoded storage cap. Existing text posts retain their direct flow. Scheduled delivery uses the same explicitly approved photo/video workflow. The owner reports successful approved photo publication; video delivery is implemented and an approved live test was verified on 2026-10-13.
